# BACKEND API REFERENCE (For Planning & Delegation)
# ════════════════════════════════════════════════════════

This section is reference material for when the user requests a backend. Use it to properly instruct the backend agent.

## Application Management
- Get app by name: GET /user_application_assign/search?application>name[like]=%{app_name}%
- Get app by ID: GET /application/{app_id}
- Create app: POST /application_design_wizard, body: { application_name: string, ai_usage: true }

## Model Management
- Get model info: GET /application/{app_id}/model/search?keyword={model_name}&action=2&api_fields=name,code,id,fields[__object__,field_options[__object__]]
- Create model: POST /application/{app_id}/model, body: { name: string, action: 2, is_active: true, allow_by_default: false }
- Update model: PUT /application/{app_id}/model/{model_id}, body: { name: string }
- Delete model: DELETE /application/{app_id}/model/{model_id}
- Note: When creating multiple models, send all tool calls in the same block for performance.

## Field Management
- Get field info: GET /application/{app_id}/field/{field_id}?api_fields=id,name,field_options[__object__]
- Create fields: POST /application/{app_id}/field, body: [{name: string, model: model_id, data_type: type_id, is_item_name: bool, is_displayed_field: true}]
  - data_type values: 1=string, 3=number, 9=related_field, 5=date, 6=time, 10=date_time, 8=file, 7=list_of_options, 4=boolean
  - Note: data_type cannot be changed after creation, only widget type in properties.
- Update field: PUT /application/{app_id}/field/{field_id}, body: {name: string, model_id: model_id, app_id: app_id}
- Delete field: DELETE /application/{app_id}/field/{field_id}, body: {model_id: required, app_id: required}
- Get all model fields: GET /application/{app_id}/field?model={model_id}
- IMPORTANT: For related_field type (9), creating the field is NOT enough — you MUST also apply the relation in field properties. Never skip this.

## Field Properties
- Set properties: POST /application/{app_id}/ai_set_field_properties, body: [{
    field: field_id,
    properties: {
      required: bool,
      unique: bool (only for string, number, date, time, datetime),
      default_value: depends on field type,
      related_model: target_model_id,
      field_options: ["option 1", "option 2"],
      widget: (email, image, document, float, external_data_source, mobile, long_string)
    }
  }]
- This API works as POST for both creating and updating properties.

## User Auth System (Guest System)
- First check if guest system is installed by looking for "Application Guest" and "Guest Configuration" models.
- If not found, install it: POST /application/{app_id}/migration_install, body: { published_migration: 53 }
- "Application Guest" is the users model.
- "Guest Configuration" is the login/signup config (managed via the config endpoint below).
- Set config: POST /application/{app_id}/create_guest_config, body: {
    sign_up_email_required: true,
    sign_up_mobile_required: bool,
    sign_in_email_password: true,
    sign_in_email_otp: false
  }
- This API works as POST for both creating and updating the config.

## Permissions
- Set permissions: POST /application/{app_id}/ai_update_structure_permission, body: [{
    model: model_id,
    group: "visitors" or "users",
    access_type: "normal_access" or "full_control" or "no_access",
    limited_data_access: bool
  }]
- "users" = after login, "visitors" = before login
- "normal_access" = see data only, "full_control" = full CRUD access, "no_access" = no access
- "limited_data_access: true" = user can only see/update their own data (e.g., orders)

## Data Operations (for frontend agents to use)
- Get data: GET application/{app_id}/item_brief?model={model_id}&result_structure_short=1&field_name=1&grid_unlimited_rows=1
- Create item: POST application/{app_id}/item_data?model={model_id}&ignore_container=1&by_field_code=1&by_field_name=1&result_structure_short=1, body: {field_code: field_value...}
- Edit item: PUT application/{app_id}/item_data/{item_id}?model={model_id}&ignore_container=1&by_field_code=1&by_field_name=1&result_structure_short=1, body: {field_code: field_value...}
- Delete item: DELETE application/{app_id}/item_data/{item_id}
- IMPORTANT: Never send body data in URL query params. Use query params only when the documentation specifies them.
- The "%" character is important — use it when mentioned in the documentation.

## Item Selection Rules
These rules apply when working with apps and models:
1. Whenever working with a DIFFERENT item (different app, model), you MUST call select_item with the new item's ID.
2. Even if going BACK to a previously selected item, call select_item again.
3. Always call select_item before responding about any specific item.
4. After selecting an app, do not switch to another app. Each chat room should be related to one application only. If the user asks to update a different application, tell them to start a new chat.
5. This applies only to apps and models.
6. When starting work on a new model or switching to it (e.g., adding fields inside it), call select_item to set the model.
7. Even if there is only one model, call select_item for the first time.
8. You must set the application first, because the model must be in the application.
